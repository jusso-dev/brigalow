# Threat model

Method: STRIDE over the data flows in [architecture.md](architecture.md), plus supply-chain abuse cases drawn from the research. Review this file whenever a trust boundary changes.

## Assets

1. Private signing keys (highest value; compromise means attacker-signed software).
2. The authority to cause a signature (credentials, approvals, release windows).
3. Audit history (needed to scope an incident).
4. Policy configuration (who may sign what).
5. Certificates and trust anchors.

## Trust boundaries

- B1 Build machine / CI job to Brigalow API.
- B2 Browser (human) to Brigalow UI.
- B3 Brigalow server to key backend (HSM over PKCS#11, cloud KMS).
- B4 Brigalow server to Postgres.
- B5 Brigalow server to gates (webhooks) and TSA.
- B6 Operator to host (deploy, config, secrets).

## Residual risks we accept and document

- Brigalow signs digests. It cannot prove the digest matches a benign artifact. Origin rules, gates and attestations reduce, not remove, this risk.
- A fully compromised Brigalow host with an activated HSM session can request signatures while it stays compromised. HSM-side key use policies, short release windows and caps limit the damage.
- Public trust depends on the CA's own controls and revocation.

## Phase 0 implementation boundaries

- B4: runtime database credentials inherit the non-owning `brigalow_app` role. Migrations run separately as an owner; the server must reject superuser, BYPASSRLS, role-management and table-owner credentials. Every tenant operation uses a transaction-local organisation context, explicit `org_id` predicates and forced row-level security. Composite foreign keys prohibit cross-tenant and cross-project references. The tenant handle is a trusted internal API, not authentication: Phase 0 has no tenant HTTP routes; Phase 1 must derive its organisation from verified identity.
- Project creation and its audit entry commit together. Per-organisation transaction advisory locks serialise audit appends, including the first append. Audit grants permit only SELECT and INSERT; tests also attempt UPDATE, DELETE and TRUNCATE as the runtime login.
- The chain uses RFC 8785 and SHA-256. Phase 0 does not yet implement signed checkpoints: an owner can rewrite the full chain or truncate its suffix without detection by the standalone verifier. Retain an independently authenticated head; AT-AUD-02 remains pending.
- Local Compose uses generated passwords, a loopback-only random Postgres port, ephemeral database storage and an isolated SoftHSM2 token directory. SoftHSM2 is a test dependency, not hardware-backed custody or a production fallback. Test IdP/JWKS and TSA services arrive with Phases 1 and 3 respectively.

- B6: configuration accepts non-secret settings and paths only. PINs/passwords come from environment variables or regular, non-symlink `0600` files (maximum 4096 bytes). Secret wrappers redact Debug; parser and driver errors are replaced with static messages. Only application logging targets are enabled, so `RUST_LOG=trace` cannot enable dependency diagnostics. The server exposes no `/debug` route. Config defaults to `production`; lab mode prints a warning and health responses label the mode. Neither mode can sign in Phase 0.
- B4 transport: server database connections require TLS with hostname and CA verification (`verify-full`), including lab mode. The acceptance harness generates a local test certificate and private key with OpenSSL, never commits either, and supplies the certificate as its trust anchor.
- B1/B2: `/healthz` is the only HTTP route, binds to loopback by default, returns no tenant data or configuration, and reports 503 when the database is unavailable. Authentication and browser sessions are not yet implemented. Do not expose this development skeleton as a production signing service.

## Phase 1 identity boundaries

- B1/B2: API access now uses an authenticated organisation, exact OIDC issuer/audience validation and a deny-by-default RBAC policy. Custodian roles cannot submit or approve, even in combination with other roles; they cannot issue submitter API credentials. API tokens are limited to a project and policy, generated with 256 random bits, stored only as SHA-256 digests, expire within 30 days, and support audited revocation. Session credentials are also hashed, expire no later than the ID token or one hour, and are revoked at logout.
- B2: public-client OIDC uses S256 PKCE, nonce verification and single-use state bound to a separate browser cookie. The callback renders an escaped, same-origin completion form so `SameSite=Strict` cookies work after a cross-site IdP redirect. Completion checks Origin and the browser-bound state; ordinary mutation forms and cookie-authenticated JSON APIs check Origin and a constant-time CSRF comparison. All cookies use Secure, HttpOnly, SameSite=Strict and host-only Path=/. Responses have no-store, no-referrer, nosniff and restrictive CSP without inline script. Askama escapes user text.
- B5 (identity provider): issuer/JWKS/authorization/token URLs come only from operator configuration, require HTTPS with verified CA/hostname, and never follow redirects. JWKS cache lifetime is 60 seconds, at most 32 keys per issuer, with response and token size bounds. Unknown token issuers never cause discovery/network calls. Workload RS256 tokens require issuer, audience `brigalow:<org>`, subject, expiry and issued-at; nbf is checked when present. Exact repository/ref/workflow/environment rules constrain scoped access. Expiry is rechecked on each request, including cache hits.
- B4: credentials and replay IDs are tenant-owned, forced-RLS tables. Project creation, request-ID reservation and audit append share one transaction. Credential issuance/revocation are audited in the same transaction. Trust configuration remains owner-controlled; a session retains its verified role snapshot until expiry/revocation. Login pending state is bounded and expires in five minutes; since migration 0010 it is shared in Postgres (see the shared login state section below).
- The local test IdP deliberately exposes token minting and invalid-token controls for acceptance tests. It binds only to a random loopback host port, creates signing keys in memory at startup, and is never a deployment component.

## Phase 2 custody boundaries

- B3: configured PKCS#11 module and exact token label are operator-owned. Startup failures never choose software. Generated RSA-3072/P-256 private objects are token-resident, sensitive and non-extractable; attributes are checked after generation. Object lookup requires exactly one class/UUID match. Public APIs return SPKI, CSRs, certificates and lifecycle metadata only. HSM PIN diagnostics remain static/redacted. SoftHSM is a disposable test emulator, not a hardware assurance claim.
- B6: `backend=software` is accepted only in lab mode; lab refuses release purpose. Software keys live in process memory and disappear on restart. Persisted metadata cannot reactivate a missing key. RSA, P-256 and Ed25519 use RustCrypto; Ed25519 raw digest signatures sign the SHA-256 digest bytes as a message, while PKCS#10 signs its complete request-info message. The HSM adapter currently supports RSA-3072/P-256, with unsupported algorithms rejected explicitly.
- B1/B2/B4: only human key custodians may generate, request CSRs, import certificates, activate, disable or retire keys. Cookie mutations require Origin and CSRF checks. Tenant resolution precedes backend access; immutable project/backend identity and optimistic revisions prevent stale metadata writes overwriting revocation. Metadata transitions and their audit entries commit together. Disable revokes database authority before disabling HSM signing. Retired keys cannot reactivate. Offline is recorded now; Phase 3 must reject offline signing until Phase 4 adds windows.
- B3/B4 have no distributed transaction: a crash during generation can leave an inaccessible orphan HSM object. Generation failure after metadata insertion is prevented by resolving the public key first; failed insertion attempts disable the object. Operator inventory/reconciliation is required for crash orphans. No automatic token resets or deletion occur. A backend-disable failure leaves the database key disabled and can be retried.
- B3/B6: imported leaf SPKI must match the generated key. RFC 5280 path, signatures, validity and required code-signing EKU are checked by rustls-webpki against configured anchors. Anchors have explicit names and `private`/`external-ca` classification. Unrecognised roots remain untrusted, software always remains lab, and neither can authorise release. No automatic public-trust classification. Revocation distribution is future Phase 7 work; this import check is not ongoing revocation monitoring.

## Phase 3 signing boundaries

- B1/B4: policies bind an active key of the same purpose and project. Binding is checked on policy creation and again against persisted rows at the signing decision; changing policy JSON directly cannot bypass it. Policies match only verified identity claims. API credentials have no synthetic OIDC claims. Release policies require explicit repository/ref/environment and `ref_protected=true`; custodians remain unable to submit. Offline keys fail closed until release-window authorisation exists.
- B3/B4: a unique request ID, immutable input/identity/policy/key snapshots and `signing` intent commit with audit before backend access. A crash leaves a stranded `signing` request; it is never automatically retried. Revocation and signing intent are serialised at the database decision: already-authorised in-flight calls may finish after a later disable. Backend and database do not share a distributed transaction. A failed final commit returns no signature, even if a backend already produced one; reconciliation uses durable intent and HSM audit, not blind re-signing.
- B2/B4: interrupted-request inspection is a GET-only, tenant-scoped route for human `OrgAdmin`/`Auditor` under `Action::Audit`, checked before lookup. It reads one request and at most 64 audit summaries, takes no locks, writes nothing, never calls a backend and returns only IDs, state and audit actions. It always reports the outcome as unknown: neither the row nor the audit log proves whether a native HSM call completed. It confers no authority to resolve, refund window capacity, release a request ID or retry. Terminal resolution would add a write path and needs a separate fencing/quiescence design and review first.
- B1/B3: only a 32-byte SHA-256 digest, bounded artifact name and explicitly self-reported metadata enter submission. RustCrypto CMS signed attributes bind digest and data content type. Raw Ed25519 signs digest bytes; CMS currently supports RSA/P-256 only because Ed25519 CMS requires SHA-512. The CLI streams the artifact through SHA-256 locally, requires verified HTTPS, follows no redirects, takes credentials from environment rather than command arguments, and never overwrites result files.
- B5: TSA URL/certificate trust is operator-configured. HTTPS verifies hostname and CA; redirects/proxies are disabled, timeout is five seconds and response limit one MiB. RFC 3161 responses require successful status, matching unpredictable nonce and signature imprint, recent generation time, a pinned signer with critical timestamp-only EKU, a valid path to configured anchors, matching CMS content-type/message-digest attributes and a verified RSA/P-256 SHA-256 signature. Token-supplied certificates cannot choose the signer or trust root. `required` failures persist a failed request and return no signature; optional omissions are explicit as an absent timestamp.
- Certificate leaf validity, code-signing EKU and digital-signature key usage are checked even when issuer trust is unknown; trusted paths are additionally validated by webpki. Signing rechecks the imported chain, preventing use after certificate expiry or anchor removal. The test TSA creates no enduring keys and has no external signing dependency.

## Phase 4 approval and notification boundaries

- B1/B2/B4: approval rules and the original verified requester are durably bound to each request. Individual decisions require a current authenticated human with the Approver role and an exact allowed actor ID. Core rejects requester/custodian decisions, including combined roles; browser buttons follow that same predicate. Askama escapes claims, metadata and artifact labels. Forms require Origin and CSRF. No bulk decision endpoint exists. Vendored htmx uses same-origin script/connect CSP; normal HTML form fallback remains available.
- Decisions, expiry, audit and final quorum transitions serialise under the tenant audit lock and request row lock. Any deny before quorum rejects; after quorum the state is closed, so a later deny cannot undo an already-authorised signature. Deadlines use database time. Pending requests survive restarts; expiry maintenance handles configured organisations with a bounded batch and read/decision checks reject expired authority.
- B3/B4: final quorum revalidates current policy/key using the original verified identity snapshot. Offline window selection and usage increment occur under lock in the same transaction as signing intent. No window or exhausted/closed/expired window fails closed. Failed backend attempts still consume capacity. Window closure and key disable cannot retract already-committed intent. Original identity/roles are a submission-time snapshot; account/role changes do not retroactively cancel pending requests. Use a deny or key disable for incident response.
- B5/B6: optional notification endpoints are operator-pinned per tenant; HTTPS hostname/CA verification, no redirects/proxies, three-second total timeout. Per-endpoint HMAC-SHA256 uses a 0600 secret file and domain-separated exact-body encoding. Only opaque tenant/project/request/event IDs and time leave this boundary; no credentials, claims, artifacts or signatures. Recipients must check timestamp and event-ID replay. Delivery success/failure is audited, never interpreted as approval. Notifications are best effort without retries; interruption may lose an event and cannot bypass pending approval. The queue is authoritative. Test receivers bind only to loopback and use generated secrets.

## Phase 5 gate and provenance boundaries

- B5/B6: pre-sign gate names resolve only within the authenticated tenant's operator-owned configuration. Per-gate secrets use 0600 files. HTTPS verifies CA/hostname, without redirects/proxies, and imposes configured bounded total timeout and 8192-byte response limit. HMAC-SHA256 signs exact request/response bytes using different domain prefixes. A random per-invocation nonce plus request ID and digest prevents response replay and cross-request substitution. Every error fails closed; no network error chooses a bypass or fallback. Only verified claims and opaque IDs/digest leave for gates, never credentials or arbitrary metadata.
- B3/B4/B5: durable `gating` intent precedes external calls. Failure records reject without backend signing. Success is audited, then current policy/key and release-window capacity are revalidated transactionally before `signing`. Window slots are consumed only at this decision. No automatic retry after crash or interrupted HTTP response. A gate's pass is necessary but cannot override tenant policy, approvals, key disable or expired/exhausted window. Individual results are visible in the approval page and audit log.
- Gate secrets let an operator of that gate answer pass/fail, not authenticate to signing APIs. A compromised required gate can falsely approve its own check; use independent gates/approval and restrict its network/secret access. The reference fixture gate proves protocol/hash comparison only, not arbitrary source reproducibility. Source execution/sandboxing remains the gate operator's boundary.
- B1/B3: optional provenance binds artifact SHA-256 and verified issuer/subject/repository/commit/workflow to an in-toto/SLSA predicate in DSSE. User metadata cannot supply builder/source fields; missing verified claims rejects. The artifact name remains an unverified label. PAE is standard protocol framing and uses existing RustCrypto/HSM signing, not a new primitive. Consumers must independently trust the public key and expected identity/source policy. This is evidence of verified workload claims, not proof that Brigalow witnessed the build or achieved a SLSA level. A cap counts signing requests; enabled provenance adds a second backend signature for that same request. No output is persisted/returned if required provenance creation fails.

Certificate import distinguishes syntax/leaf constraints from trust establishment: with no configured anchors, a syntactically valid bundle with matching SPKI, current leaf validity, code-signing EKU and digital-signature usage remains `untrusted`, including bundles carrying a self-signed root. Supplied roots never become trust anchors. CA certificates cannot be used as signing leaves. Only configured-anchor webpki validation establishes private/external-CA classification; an untrusted label makes no claim that an unknown chain's signatures were authenticated.


## Phase 6 native-client and action boundaries

- Native tools load a PKCS#11 client in their own process. Its narrowly permitted unsafe C ABI assumes valid aligned caller buffers; null/length checks, a 64-session limit, 16 MiB input-chunk limit and panic containment bound normal calls. Native code sharing the process already controls its environment credential and memory; this is not a sandbox. Mutex initialisation callbacks are rejected unless OS locking is permitted. No private-key, generation, wrapping, decryption or mutation operation is exposed. SHA-256 DigestInfo is validated strictly; hashing streams stays local.
- Operator-selected client HTTPS origin/policy and CA files are part of the build-host trust boundary. TLS verifies hostname/CA; no redirects, environment proxies or automatic submission retry. Responses are bounded and matched against request ID, digest, policy, project and public key. Environment credentials authenticate every server call; PKCS#11 login supplies no additional authority. Length queries and small output buffers never submit. Approval/gate/window/key checks remain authoritative server-side. The token model reports lab/private/external-ca/untrusted classification, never hardware assurance.
- GitHub's runner-provided token endpoint is contacted with its mint credential only over verified HTTPS, no redirects/proxies, exact organisation audience and bounded response. Only the resulting short-lived token enters the CLI child environment; neither credential is put in argv or diagnostic output. Workflow input is passed through environment variables, never interpolated as shell source. The action's source revision and build dependencies must be reviewed/pinned by consumers.
- Tool acceptance runs in an internal Compose network with no external egress. CA/JWKS/TLS credentials are generated per run. Cosign transparency upload is disabled; GPG uses a disposable home and existing remote key reference. No real CA, transparency service or signing account is contacted.


## Phase 7 private CA boundary

- The optional `brigalow-ca` operator process is separate from HTTP signing. Its root is offline/external; its intermediate uses a dedicated PKCS#11 token/configuration, with no software fallback. Public issuer references are never inserted into ordinary signing-key/policy tables. The CA database login inherits only `brigalow_ca`; the web login cannot read/write CA ledger tables, and the CA login cannot mutate signing keys/policies. Forced tenant RLS, explicit org predicates and append-only shared audit apply. Provisioning and profile configuration are trusted operator actions, not caller metadata.
- Profiles are immutable by UUID, use only an operator-owned private-enterprise OID arc, and pin subject identity. CSR signatures prove possession using RustCrypto; CSR-requested subjects/extensions are ignored. Issued leaves have codeSigning EKU, digitalSignature usage, CA=false and exactly 72-hour validity. Full chain/signature/constraint validation uses webpki against explicit private roots at both validity endpoints. Bundled roots do not grant trust. PEN ownership cannot be verified automatically and is an operator responsibility.
- A DB-clock UTC-day reservation and random serial commit before HSM issuance. Unique org/profile/day prevents concurrent duplicate issuance and rotation bypass. Failures retain unresolved intents; there is no automatic retry. Signed outputs commit before public-file export. Revocation can also cancel an interrupted intent, preventing late completion. CA records and audit have no DELETE/TRUNCATE grants; profile records have no UPDATE grant. Only the CA role may complete output/revocation fields.
- CRLs snapshot committed revocations, reserve monotonic numbers and commit only if no revocation was omitted and no newer publication was reserved. They expire after 24 hours. The operator distributes the signed public file and ensures consumer freshness; Brigalow opens no CA HTTP listener or production deployment. A compromised operator/HSM or CA DB login remains inside the issuer administration boundary. Restoring an older ledger can lose revocations; backup/restore must reconcile the latest externally retained CRL/audit head before signing resumes.
- Timestamp-backed historical validation requires authenticated TSA signature/path/imprint and uses its genTime, never caller metadata. Expired leaves fail ordinary current-time verification. Timestamps do not negate revocation, root trust changes or TSA compromise. No public trust or compliance assurance is asserted.


## Phase 8 operations boundaries

- Authenticated credential/session budgets are enforced on the DB clock under the tenant audit lock and shared across replicas. Verified workload actor/scope is the stable budget identity, preventing JWT-refresh bypass. Invalid identities confer no budget authority; ingress must independently bound unauthenticated verification/login traffic. Per-window audit aggregation limits log amplification. Body limits remain 64 KiB. Cleanup is tenant-scoped and bounded; DB failure does not bypass limits.
- Audit checkpoint signing uses a separate operator HSM key, never a policy/CA key. Canonical, domain-separated signatures bind org/sequence/hash/time/key/algorithm. The exported prefix is verified before signing, and signed records are append-only. Offline verification requires an independently pinned public key and exact checkpoint head. External retention is required to detect rollback to an older valid checkpoint; an included key alone proves no identity. Restoring old databases can lose revocations/caps and requires reconciliation, not automatic continuation.
- Checkpoint retention boundary (AT-AUD-03): trust in a checkpoint comes from two inputs held outside the Brigalow DB and signing host, under a separate administrative boundary: the audit public key, pinned through an independent channel, and the latest expected head `(org, seq, entry_hash)`. A public key or marker shipped inside a bundle proves no identity, and a local file on the same host is not independent. `brig audit verify --expected-head` rejects older (rollback), newer-than-recorded and substituted valid checkpoints. Without it the verifier reports only "cryptographically valid prefix; freshness unknown". `brigalow-audit recover` reads an already persisted record under tenant RLS, verifies it with the operator-supplied pinned key and the exact prefix, and loads no key backend, so it cannot sign or create a record. A record an attacker inserts with DB write fails that verification unless the attacker also holds the HSM key. Output bundles are staged privately and published whole with a kernel no-replace rename; the completion marker binds digests but authenticates neither publisher nor freshness. An absent record does not show that the HSM did not sign during an interrupted attempt. Off-host transport, immutability and updating the expected-head record are operator-owned and not provided or verified by Brigalow.
- Backup drills destroy only a uniquely named disposable scratch DB and preserve HSM key custody. Real HSM backup and operator secret distribution remain outside the application boundary. The draft chart copies projected secrets to private 0600 regular files, uses a non-root restricted container and exposes ClusterIP only; TLS ingress/network policies/vendor providers are operator-managed and no cluster was deployed.
- Bounded nightly parser fuzzing is test instrumentation only; application builds stay stable. The release workflow signs artifacts through an ephemeral lab control plane and labels that limitation explicitly. Bundled lab keys provide no independent publisher authentication. SBOMs/checksums/signatures are public outputs, not private keys or assurance certificates.

## Phase 9 remote mock boundary

- B3 now includes a local CSC v2 mock transport. Operator-selected references bind credential ID, key UUID, organisation, project and exact leaf certificate. Cross-scope registration returns 404; duplicate registration cannot disable a previously registered reference. Runtime DB authority still controls activation, policies, approvals, gates and windows.
- `csc_mock` refuses production mode and non-loopback origins. TLS validation, no proxy/redirect, bounded response size/time and no automatic retry prevent endpoint redirection and unbounded remote operations. Acceptance runs inside an externally isolated Compose network. No real remote CA endpoint has been tested.
- Authorisation binds exactly one SHA-256 digest, uses a fresh ephemeral SAD and checks positive expiry. The upstream mock enforces digest binding, expiry and single use. Unsupported auth flows fail closed; there is no MFA bypass. RustCrypto verifies the returned RSA-3072 signature against the pinned key before persistence. Failures produce no output, even when a remote signature might already have happened.
- Bearer/SAD secrets are never logged or audited. Owned buffers are zeroised where practical; transport-library copies and a compromised process remain residual risks. Disable stops Brigalow authority, not the upstream credential; separate upstream revocation remains an operator responsibility. The mock always remains `lab`; `external-ca` elsewhere is operator anchor classification, never platform acceptance.

## Production reference and dependency remediation boundaries

- B1/B2/B6: the single-instance reference places a non-root TLS proxy in front of an unpublished HTTP listener. It bounds bodies, headers, connections, request rate and timeouts; ignores caller-supplied forwarding identity; disables request/error logs that could expose OIDC codes; and never retries upstream signing. TLS material and runtime credentials are operator-provisioned read-only files. The Helm NetworkPolicy defaults to deny and requires explicit egress; actual CNI/ingress enforcement remains an operator qualification. AT-OPS-05 exercises the real image/proxy with generated local credentials.
- B3/B4/B6: production refuses disabled/lab backends, missing identity, failed provider initialisation and schema drift. Readiness checks DB and authenticated HSM session with a bounded wait, without generating signatures. Native provider calls cannot be forcibly cancelled; a nonblocking session lock prevents health probes queuing unbounded work behind a stuck provider. Vendor transport limits and recovery remain required.
- B4/B6: `brigalow-admin` is an explicit owner-only migration/bootstrap process. Owner credentials never enter the runtime reference. SQLx controls migration locks/checksums; runtime sees SELECT-only migration history and rejects missing/extra/failed/changed migrations. Organisation creation and its audit entry commit atomically; repeated UUID/name is idempotent and conflicts reject. AT-OPS-04 checks these boundaries.
- B2/B5: dependency remediation replaces the old OIDC adapter with OAuth2 PKCE construction and jsonwebtoken/AWS-LC signature verification. In addition to issuer/audience/expiry/subject checks, ID tokens require matching nonce, integer issued-at (30-second future clock tolerance) preceding expiry, exact single audience and matching azp when supplied. JWT critical/content-type headers, unsupported types, duplicate key IDs and incompatible JWK usage/algorithm/operations fail closed. AT-ID-01/02 exercise signed local IdP tokens. Only the documented RS256 public-client flow is supported; this is not a new cryptographic implementation.
- B6/supply chain: both application and fuzz lockfiles are audited with warnings denied, no advisory exceptions. Scheduled hosted audits detect future advisories. Builder/runtime/proxy images and Actions are pinned; OS/provider packages still require operator image scanning and patch management. Software/reference tests do not qualify an actual HSM, production restore, HA topology or deployment configuration. The chart enforces one replica.

## GitLab workload profile boundary

- B1/B6: the workload token profile is operator configuration on each authority (`provider`, default `github`). It is never inferred from token contents, issuer host or caller metadata. One issuer cannot be configured under two profiles in the same organisation, so profile selection never depends on configuration order. GitHub authorities keep the exact raw-claim matcher and the original fixed claim set; their principals carry no `provider` claim.
- B1: GitLab checks run only after the existing RS256 signature, pinned issuer/JWKS, exact `brigalow:<org>` audience, expiry, nbf and at-most-3600-second lifetime checks. Each GitLab rule pins the issuer-scoped project ID and path. Signed `job_project_id`/`job_project_path` (documented from GitLab 18.4) and source `project_id`/`project_path` must all equal them, so missing job claims (older instances) and mixed job/source pipelines fail closed. `ref_path` must be `refs/heads/<name>` or `refs/tags/<name>`, consistent with `ref_type` and short `ref`, and equal the configured fully-qualified ref; only this verified `ref_path` becomes canonical `ref`. `ref_protected` must be the JSON string `"true"`, matching the documented GitLab example; booleans and other forms are rejected until a reviewed contract establishes them. `pipeline_source` must be in an exact operator list; merge-request and external pull-request sources cannot be configured. A configured environment must match exactly; absent, null or non-string values fail. `sha` must be 40 or 64 lowercase hex characters. All signed values must be non-empty JSON strings.
- B1: GitLab principals are normalised to `provider = "gitlab"`, `iss`, `sub`, `ref`, `ref_type`, `sha`, the pinned project IDs/paths, `pipeline_source`, optional `environment` and numeric `pipeline_id`/`job_id`. No `repository`, `workflow` or `ref_protected` canonical claim is produced, and `ci_config_ref_uri` is not mapped to `workflow`: it names only the top-level configuration ref. A GitLab token that itself carries `repository`, `workflow`, `job_workflow_ref`, `run_id` or `provider` is ambiguous and rejected rather than reinterpreted.
- B1/B4: `brigalow-core` policy authorisation rejects any principal carrying a `provider` claim for `release` policies and for attestation-enabled policies (`provider_purpose`), at submission, approval quorum and gate revalidation. GitLab authority therefore reaches only `test` signing without DSSE provenance. Release and attestation need a separately reviewed, versioned contract for protected refs, environment protection, job/source project relationships and pipeline configuration provenance.
- Lifetime incompatibility: GitLab ID tokens expire at the job timeout (five minutes when unset). Brigalow keeps its 3600-second maximum lifetime, so a job whose timeout exceeds one hour receives a validly signed token that Brigalow rejects. Operators must keep signing jobs at or below a one-hour timeout; the limit is not weakened for this provider.
- Residual: GitLab version and project identity are operator-asserted, not verified. Distinct GitLab instances can reuse project IDs, so the issuer pin remains mandatory. A project transfer or rename changes the path and fails closed; a deleted and recreated project gets a new ID. AT-ID-04 uses generated tokens shaped from public documentation and does not qualify any real GitLab release.

## Shared login state boundaries

- B4 now holds encrypted PKCE material. Pending OIDC logins are tenant-owned, forced-RLS rows. Each row holds the SHA-256 state hash, provider, SHA-256 browser-binding hash, DB-clock expiry, key ID/version and an AES-256-GCM ciphertext of the PKCE verifier and nonce. The cipher is `aws-lc-rs` `RandomizedNonceKey`, which generates every nonce itself. The associated data binds version, org UUID, provider, state hash, browser hash, expiry and key ID, so ciphertext cannot be moved between rows, tenants, providers or browsers. The runtime role has SELECT/INSERT/DELETE only (no UPDATE). A database reader, backup or owner operator sees no plaintext verifier or nonce. To complete a login, an attacker needs the operator key, the authorisation code and the victim's browser cookie together. [ADR 0004](decisions/0004-shared-login-state.md).
- B6: the 256-bit login-state key is a dedicated operator secret, separate from HSM PINs, signing keys and DB credentials. It loads through the redacted secret-file loader: regular, non-symlink, 0600, base64 of exactly 32 bytes. Only explicitly configured previous key IDs can open old rows; unknown IDs and failed authentication reject. Keys are never generated per instance. Human login refuses to start without a key ring. A shared counter limits each key ID to 2^31 committed seals and fails closed beyond that. Rotating or withdrawing a key invalidates only pending logins sealed with it; existing sessions follow their own expiry and revocation.
- B2/B4: login creation enforces per-tenant (1024) and global (4096) live-row bounds under one transaction advisory lock, so concurrent instances cannot overshoot them. The global inventory holds only a random slot UUID and expiry. The callback deletes and locks the exact row in a tenant transaction. It checks DB-clock expiry, provider, version, constant-time browser hash and AEAD authentication, and commits consumption only when all pass, before the token exchange. A wrong browser, provider, organisation, key or tampered row rolls back without consuming. Racing callbacks on different instances produce at most one exchange. A database failure rejects the login, with no in-memory fallback. Expired rows are removed in bounded batches on the DB clock.
- Residual: a compromised application process holds the key ring and handles plaintext during login. Encryption at rest does not protect against that, nor against a DB writer deleting pending rows (denial of login). The global bound lets one tenant's unauthenticated login traffic exhaust the shared inventory for five minutes, so ingress rate limits remain required. This change does not establish HA: one replica remains the only supported topology, and AT-HA-02 signing/HSM concurrency is not implemented.

## Operator release-signing boundaries

- B1/B6: an operator release bundle is authenticated only by a public key the consumer pins through a separate trusted channel. A key, certificate or fingerprint shipped in or beside the bundle cannot establish identity, and the verifier refuses a pinned key located inside the bundle. A verifier pass means the signature is valid for that key and the bundle declares `operator` origin. It is not a public-trust, CA or platform-trust claim, and it cannot detect a withheld newer release.
- B1: the signed object is the exact canonical manifest bytes. The verifier checks the signature with OpenSSL before parsing, then enforces a strict schema and reads only regular files directly inside the bundle. Lab version 1 and operator version 2 are separate modes with no fallback between them.
- B1/B3: the workflow submits one request through the normal release policy, approval, gate and window path. It never retries, bypasses the server or reaches the HSM directly. An uncertain result (timeout, interruption) is reported with its request ID for operator inspection; any release-window capacity it consumed stays consumed.
- B6: publication uses an atomic no-replace rename and fails closed where none is available. Staging sits beside the output on the same filesystem and is removed on failure. Choosing, rotating and revoking the pinned key, and the channel used to distribute it, remain operator responsibilities.
